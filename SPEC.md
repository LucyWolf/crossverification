# CrossVerification — Protocol Specification

**Version 1.0** · status: stable · last change: 18 November 2026

A small HTTP protocol that lets one Discord bot ask another: *do you vouch for this user?*

It exists because the same work gets done over and over. A community vets its members —
age checks, VRChat account ownership, an application, whatever their bar is — and hands out
a role for it. A partner community trusts that work but cannot see it, so everybody goes
through the same process a second time. CrossVerification lets the second community accept
the first one's answer, without either side handing over a member list.

Nothing in here is specific to any one bot. Two implementations that follow this document
can talk to each other.

---

## 1. Roles in a conversation

| | |
|---|---|
| **Issuer** | The side that did the vetting and answers questions about it. It issues the key. |
| **Relying party** | The side that asks, and grants something based on the answer. |

A pair is one-directional. Two communities that want to trust each other both ways set up
two pairings, one in each direction, with two different keys. This is deliberate: trust is
rarely symmetric, and revoking one direction must not take the other one with it.

## 2. Authentication

A pairing is identified by one **key**: an opaque string, generated by the issuer, handed to
the relying party out of band (copy it into a chat, an email, a form — this protocol does
not cover the handover).

- The key MUST be unguessable. Implementations SHOULD use at least 32 bytes from a
  cryptographically secure source.
- The issuer MUST be able to revoke a key and issue a new one without disturbing other
  pairings.
- The issuer SHOULD store only a hash of the key (SHA-256 is enough; the key is a random
  secret, not a password, so no stretching is needed). It is only ever compared, never read
  back — so a leaked database does not leak the keys.
- The key MUST be sent in the request body, not in the query string. Query strings end up
  in server logs, proxy logs and browser history.

There is no account, no registration and no central directory. Whoever holds the key is the
partner; whoever revokes it ends the pairing.

## 3. Transport

- HTTPS SHOULD be used. Over plain HTTP the key travels in clear text and anybody on the
  path can take it.
- Requests are `POST` with `application/x-www-form-urlencoded` bodies.
- Responses are JSON.
- A relying party MUST NOT follow redirects. A pairing points at one address; a redirect is
  either a misconfiguration or somebody steering the request elsewhere.
- A relying party MUST limit how much of a response it reads. 64 KiB is plenty for every
  answer this protocol defines.
- A relying party MUST use a timeout. Eight seconds is a reasonable default.
- A relying party MUST refuse addresses that do not resolve to public IP addresses, and MUST
  check **every** address a name resolves to, not just the first. The server sits inside a
  network and can reach things the person who configured the pairing never could —
  `127.0.0.1`, `10.0.0.0/8`, a cloud provider's metadata endpoint. Without this check the
  pairing form is a tool for scanning the issuer's own network.

## 4. Endpoints

### 4.1 `POST /coop/check` — does this user count as verified?

**Request**

| Field | Type | |
|---|---|---|
| `key` | string | the pairing key |
| `user_id` | string | the Discord user id, digits only |

**Response** `200`

```json
{ "verified": true }
```

That is the whole answer, and it is the whole answer on purpose. No name, no roles, no hint
about whether the person is a member at all. **A `false` means "not verified" and nothing
else.** Whoever holds the key should be able to honour verifications — not walk the member
list.

| Status | Meaning | Body |
|---|---|---|
| `200` | Answered. | `{"verified": true}` or `{"verified": false}` |
| `400` | `key` or `user_id` missing or malformed. | `{"verified": false}` |
| `403` | Key unknown, revoked or disabled. | `{"verified": false}` |
| `429` | Too many requests for this key. | `{"verified": false, "error": "too many requests"}` |

A `403` is the only status that says something about the **pairing** rather than the person.
A relying party SHOULD use it to mark the pairing as broken and tell its admin, instead of
quietly asking forever.

The issuer MUST answer `403` for an unknown key with the same body as a `false` answer. A
response that distinguishes "I don't know that key" from "I don't know that person" turns
the endpoint into an oracle for guessing keys.

### 4.2 `POST /coop/info` — who are you, and what do you share?

**Request**

| Field | Type | |
|---|---|---|
| `key` | string | the pairing key |

**Response** `200`

```json
{ "ok": true, "server": "Example Community", "roles": ["Verified 18+", "Trusted"] }
```

For setup only: the relying party's admin sees what the other side actually shares and
decides what to grant for it, instead of guessing what a role over there is called.

Returned are the **names** of the roles this pairing shares and the server's name. Not the
other roles, not any ids, nothing about members.

| Status | Meaning | Body |
|---|---|---|
| `200` | Answered. | as above |
| `400` | `key` missing. | `{"ok": false}` |
| `403` | Key unknown, revoked or disabled. | `{"ok": false}` |
| `429` | Too many requests for this key. | `{"ok": false, "error": "too many requests"}` |

## 5. Rate limiting

An issuer MUST limit requests per key. 60 per minute is a sane default: a relying party asks
when somebody joins or when a scheduled sync runs, not continuously. Anything far above that
is either a loop or somebody enumerating user ids.

Counting per **key** rather than per address is deliberate — a partner behind a changing
address is still one partner, and a shared address is still several.

## 6. Fail closed

Any outcome that is not an explicit `{"verified": true}` is a **no**: timeout, DNS failure,
`500`, unparseable body, a redirect, a body too large, a certificate error.

Granting something because a request ended unclearly is the exact opposite of what a
verification is for. There is no retry-until-yes.

## 7. What this protocol deliberately does not do

- **No member lists.** There is no endpoint that enumerates anybody. Every question is about
  one user id that the asker already knows.
- **No personal data.** No names, no email addresses, no dates, no reasons. The answer is one
  bit.
- **No revocation push.** An issuer does not notify when somebody loses a role. A relying
  party that cares re-asks on a schedule. Pushing would need a callback address, a second
  key, and delivery guarantees — for a system where asking again costs one request.
- **No central registry.** Nobody runs a directory of participants, and there is nothing to
  sign up for.
- **No transitive trust.** An answer covers what *this* issuer vetted. If A trusts B and B
  trusts C, that does not make C's verifications valid for A. Implementations MUST NOT chain
  requests.

## 8. Privacy note for operators

A `true` tells the asking side that the person is known here and holds a shared role. That
is a statement about a real person, made to a third party. Before setting up a pairing, make
sure your members know that holding the role is what gets shared, and share only roles where
that is defensible. The protocol keeps the payload to a minimum; it cannot decide for you
whether the pairing should exist.

## 9. Versioning

This document is version 1.0. Field names, status codes and their meanings will not change
within version 1. New optional fields may be added; an implementation MUST ignore fields it
does not know.

A breaking change gets a new path prefix (`/coop/v2/check`), so both can be served side by
side.

## 10. Conformance

An implementation conforms if it:

1. serves both endpoints with the status codes and bodies above,
2. stores keys hashed and can revoke them,
3. rate-limits per key,
4. answers unknown keys indistinguishably from a `false`,
5. and — as a relying party — refuses non-public addresses, refuses redirects, limits
   response size and time, and treats every unclear outcome as a no.

The test suite in `tests/` checks all of these against any implementation reachable over
HTTP, not just the reference one.
